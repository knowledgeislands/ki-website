# TRD-497d3cf3: Document repository taxonomy and work tracking

## Context

The change-management adapter discussion exposed an unclear repository taxonomy. The current configuration distinguishes only an implicit ordinary repository and a Knowledge Base, while repository structure skills and optional capabilities are separate dimensions. Website documentation will eventually need a clear explanation before external tracker adapters are introduced.

## Submission

Publish an approachable guide that separates: (1) operating model — Project or Knowledge Base; (2) primary work tracker — project roadmap, Streams, GitHub Issues, or Linear; (3) primary structure — for example harness, website, MCP server, tool, plugin, specifications, or dotfiles; and (4) optional capabilities such as engineering, skills, subagents, checkpoints, and trades. Make the harness contract and configuration reference canonical; the website should explain the model, provide examples, and help a reader choose.

## Constraints

This is knowledge, not a request to implement a tracker or alter the website now. Treat Project and Knowledge Base as the proposed operating-model vocabulary pending the harness taxonomy decision. Preserve website editorial ownership; do not infer an approved migration from the current repository value or from this trade.
